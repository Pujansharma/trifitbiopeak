and selectively integrating the ROOK/wearables implementation from
`Biopeak-Nexus-BE-Phase1-PRD-Updated(1).zip`. It is **not** a snapshot of the client's
live GitHub main/develop branch. Compare against that branch and resolve conflicts before PR.

## What IS integrated

- `wearables/` — profile-level ROOK IDs, consent, provider connections, raw documents,
  canonical observations, daily summaries, snapshots, retryable processing,
  metrics/trends, six health domains, timeline and tests.
- `webhooks/rook/` — signed data/notification webhook endpoints.
- `GET /devices/`, `POST /devices/connect/`, `/disconnect/`,
  `/retry-sync/`, `POST /devices/revoke-consent/`, `GET /api/v1/devices/sdk-config/`, `POST /api/v1/devices/native-status/`.
- `GET /health/dashboard/`, `/health/{domain}/?days=7` or `days=30`,
  `/health/timeline/` (its filters are `start`, `end`, `domain`, `offset`, `limit`).
- These paths are at the root in the supplied Django URL configuration; a deployment proxy may prepend `/api/v1/`. Verify the live API base URL with the frontend team.
- Management commands `process_health_jobs`, `enqueue_health_freshness_checks`,
  `health_phase1_status`, and dry-run raw-payload purge. The worker command additionally accepts optional
  `--customer-profile-id UUID --limit N` to process only that member's queued jobs.
- CORS headers, Django app registration, per-profile feature tab, environment-scoped
  ROOK credentials and database-revisioned Django health cache settings.

## Build and deployment blockers — DO NOT claim production acceptance yet

1. **Dependency resolution:** The unintended Redis dependency has been removed, restoring
   consistency with the original `uv.lock`. Verify with `uv sync --frozen` on a Python 3.14 host.
   The client Dockerfile is unchanged.
2. **Django checks/migrations/test suite were not executed** here because
   Python 3.14 and required packages/PostgreSQL 17 were unavailable.
3. ROOK production authorizer, signed delivery, mobile SDK backfill, React Native
   UI, detailed diagnostic biomarker timeline, clinical trend thresholds, DPDP compliance,
   production monitoring and load testing require client/external validation.
4. Production uses feature flags (default OFF). Enable only after staging sign-off.
   The Django health cache uses a process-local backend plus DB revision key;
   verify multi-instance freshness and load before considering shared Redis.
5. Cron or background worker deployment is still required; a management command
   does not automatically create a scheduled worker in Render.
6. The user has now provided **Biopeak Longitudinal Health Platform — PRD (1).html** (draft v1.0).
   Review the companion `docs/PHASE1_PRD_FIXES_AND_REMAINING_GATES.md` for the
   items that cannot be completed or validated solely within the backend archive.

## Safe review and deployment workflow

1. Pull current client main/develop into a fresh branch.
2. Apply the additions and targeted edits from this ZIP; inspect the manifest/diff.
3. Check client migrations after 0019 and organization migrations after 0002 for conflicts.
4. On Python 3.14, run `uv sync --frozen` against the unchanged original lockfile.
5. Run `uv run python manage.py check` and
   `uv run python manage.py makemigrations --check --dry-run`.
6. On staging Postgres 17, run `uv run python manage.py migrate --plan`,
   inspect generated SQL, back up DB and apply migrations.
7. Run `uv run python manage.py test wearables` and existing backend regression tests.
8. Test 7-day/30-day card and metric responses, per-reading timestamps, permissions, webhook signatures/replays, processing,
   ROOK user ownership, source reconnect/history, and provider error/empty states.
9. Run the Render worker only after validating DB and the job locking design.
10. Push a feature branch, open a PR, have the client review before merge.

### Worker examples

```bash
python manage.py process_health_jobs --limit 5 --verbosity 2
python manage.py process_health_jobs --customer-profile-id <UUID> --limit 1
python manage.py enqueue_health_freshness_checks
python manage.py health_phase1_status --hours 24
```

Run the commands with the correct `DJANGO_SETTINGS_MODULE` and credentials.
The background job count limits jobs, not generated health observations.
