# Biopeak Backend — Plain-English Change Guide

**Purpose:** This document explains what was brought into the merged backend, what was changed, what files were added, and what still needs testing. It is written so a non-developer can explain the work in a review or handover.

## 1. Short explanation you can say to someone

> I created a separate copy of the old Biopeak backend and merged the Phase 1 ROOK backend changes into it. I kept files that existed only in the old project, brought in the new features and supporting files from the new project, and made six Python exception-handling syntax fixes so those files can be parsed by Python. I also documented the merge. I checked Python syntax and ZIP integrity, but the application still needs Django checks, database migration testing, and API/integration tests in a configured environment.

## 2. What I did (in simple terms)

1. **Protected the original projects.** The uploaded old and new ZIP files were not overwritten. Work was done in a separate merged folder.
2. **Used the old backend as the base.** Existing old-only files were kept.
3. **Copied in the new Phase 1 ROOK snapshot.** Where a file existed in both versions and differed, the newer version was used in the merged copy.
4. **Kept new feature files.** This includes the wearable/ROOK app, device and health URL routes, appointment-related files, product document-category support, configuration, tests, documentation and API request examples where present in the new snapshot.
5. **Fixed six Python syntax errors.** The old and new snapshots contained invalid exception syntax in six files. In the merged copy, these handlers now use valid tuple syntax for handling multiple exception types.
6. **Added this explanation and a machine-readable manifest** so another developer can audit the merge.

## 3. Features and areas included

| Area | Plain-English purpose | Where to look |
|---|---|---|
| ROOK / wearable support | Handles device-related and health-data API routes and ROOK webhook-related backend code. | `wearables/`, project URL configuration, `.env.example` |
| Device API routes | URL definitions for device-related endpoints. | `wearables/device_urls.py` |
| Health API routes | URL definitions for health-related endpoints. | `wearables/health_urls.py` |
| Appointments | Booking/customer/care-team URL and supporting model/permission/test files from the new snapshot. | `appointments/` |
| Products / document categories | Product API and model/serializer/view changes from the newer snapshot, including document category support where implemented. | `products/` |
| Integrations | Supporting integration app files from the newer snapshot. | `integrations/` |
| Diagnostics orders | Diagnostics order app files included in the new snapshot. | `diagnostics_orders/` |
| Test-kit inventory | Test kit inventory app files included in the new snapshot. | `test_kit_inventory/` |
| Existing backend features | Old-only files remain in the merged project rather than being deleted just because they were absent from the new snapshot. | Relevant existing app folders |
| Developer/configuration support | Environment example, Docker/project setup, tests, documentation and Bruno API request collection files included in the snapshots. | `.env.example`, `README.md`, `docker-compose.yml`, `bruno/`, app `tests.py` files |

**Important:** The presence of a route/model/file does not by itself prove the feature works end-to-end. That requires running the app with its dependencies, environment variables, database, and any external ROOK credentials configured.
